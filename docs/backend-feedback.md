# Замечания к API: auth, advertisers, contracts и campaigns

Собрано при подключении фронта к стенду `https://setanta.pythonanywhere.com`.
Каждый пункт проверен запросом, ответ сервера приведён. Раздел `channels`
пока не смотрели.

Сверялись со схемой `/api/v1/schema` и с `docs/backend-spec.md`.

---

## Блокирующее

### 1. CORS не настроен

Preflight отвечает `200`, но без единого заголовка `Access-Control-Allow-*`,
поэтому браузер не пропускает ни один запрос:

```
Access to fetch at '…/auth/login' from origin 'http://localhost:5180'
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header
is present on the requested resource.
```

Фронт временно ходит через прокси (`server.proxy` в разработке, `rewrites`
в продакшене), но это обход, а не решение: любой сторонний клиент упрётся
в то же самое.

**Нужно:** `django-cors-headers` с белым списком origin'ов фронта.

### 2. Выйти с истёкшим access нельзя

`POST /auth/logout` требует `Authorization`, а access живёт 15 минут. Если он
истёк, выход не проходит:

```
POST /auth/logout   (Authorization: Bearer <протухший>)
→ 401 {"error":{"code":"token_not_valid",…}}
```

Refresh при этом остаётся живым на сервере — то есть пользователь нажал
«Выйти», а сессия на сервере не погашена. Клиент вынужден просто забыть
токены локально.

**Нужно:** разрешить `/auth/logout` без `Authorization` — присланный refresh
сам по себе достаточное доказательство владения сессией. Либо гасить refresh
даже при истёкшем access.

### 3. Номер договора не уникален

`docs/backend-spec.md` (§2.3): «`number` — уникален **по всей базе**».
Фактически дубликат создаётся:

```
POST /advertisers/3/contracts {"number":"Д-2026/1001", …}
→ 201 {"id":19,"number":"Д-2026/1001", …}
```

При этом `Д-2026/1001` уже принадлежал другому бренду. Кампания ссылается на
договор по номеру, поэтому дубликаты сделают выбор договора неоднозначным.

**Нужно:** `unique` на номер и `409`/`400` с полем `number` в `fields`.

## Расхождения схемы и поведения

### 4. `paymentStatus` приходит пустой строкой

В схеме поле обязательное и ограничено `PaymentStatusEnum` (`awaiting` / `paid`),
а сервер отдаёт пустую строку:

```
GET /advertisers/10 → contracts[0].paymentStatus == ""
```

Клиенты, сгенерированные по схеме, на этом ломаются: пустая строка не входит
в перечисление.

**Нужно:** либо добавить пустое значение в enum (как сделано для `package`
через `BlankEnum`), либо возвращать `null` и пометить поле `nullable`.

### 5. У договора есть `file` и `creative`, но их нет в схеме

Сервер возвращает их в каждом договоре:

```json
{"number":"Д-2026/902", …, "file":null, "creative":null}
```

В `components/schemas/Contract` этих полей нет. Непонятно, доступны ли они на
запись и в каком виде, поэтому фронт их не отправляет — раздел «скан договора»
и «ролик» в форме сейчас не сохраняется.

**Нужно:** описать поля в схеме (тип, доступность на запись) или убрать из ответа.

### 6. Ответ 409 при устаревшем `version` не описан

Механизм работает — и это хорошо:

```
PATCH /advertisers/3 {"contact":"…","version":1} → 200
PATCH /advertisers/3 {"contact":"…","version":1} → 409
```

Но в схеме у `PATCH` только `200`, про `409` и про сам смысл `version`
ничего не сказано. Важнее другое: **без поля `version` проверка не
выполняется** — запрос проходит и молча затирает чужие правки:

```
PATCH /advertisers/3 {"contact":"…"}   → 200, без проверки версии
```

**Нужно:** описать `409` в схеме и решить, обязателен ли `version` при
изменении. Если он не обязателен, защита фактически необязательна и её легко
обойти по невнимательности.

### 7. `leagues` в схеме без типа

`Contract.leagues` описан как `leagues: {}` — по факту это массив строк
(`["epl","laliga","seriea"]`). Генераторы типов дают `any`.

## Формат ошибок

### 8. Ошибки JWT нарушают собственный контракт

Описано: `fields` — «ошибки по полям формы; пусто, если ошибка не про поля».
Фактически при невалидном токене туда попадают внутренние данные библиотеки:

```json
{
  "error": {
    "code": "token_not_valid",
    "message": "Данный токен недействителен для любого типа токена",
    "fields": { "code": "token_not_valid", "messages": "AccessToken" }
  }
}
```

`fields` здесь не про поля формы, а `message` — техническая фраза, которую
нельзя показать пользователю.

**Нужно:** для 401 оставлять `fields` пустым, а `message` писать человеческим
языком («Сессия истекла, войдите заново»).

Для сравнения, обычная валидация оформлена правильно и вопросов не вызывает:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте заполнение полей",
    "fields": { "email": "Введите правильный адрес электронной почты." }
  }
}
```

## Чего не хватает для интерфейса

### 9. Загрузка файлов появилась — закрыто частично

Само поле `logo` работает — но принимает только абсолютную ссылку:

| Что отправили                  | Ответ                                      |
| ------------------------------ | ------------------------------------------ |
| `https://example.com/logo.png` | `200`, значение сохранено                  |
| `/logos/artel.png`             | `400` `{"logo":"Введите правильный URL."}` |
| `data:image/png;base64,…`      | `400` `{"logo":"Введите правильный URL."}` |

В форме логотип выбирают файлом, а файл живёт как `data:`-URL — то есть
отправить его некуда, да и в 500 символов он не помещается. Мы добавили
в форму поле для ссылки: так логотип сохраняется. Выбранный файл показывается
для предпросмотра, но на сервер не уходит, и форма об этом предупреждает.

То же касается скана договора и рекламного ролика (см. п. 5).

**`POST /files` работает** — скан договора и ролик подключены через него
(см. п. 21). У логотипа бренда остаётся прежняя проблема: поле принимает
только абсолютный URL, а загрузчик отдаёт свой, относительный — и он же
закрыт токеном (п. 22). Поэтому логотип по-прежнему хранится ссылкой,
а выбранный файл показывается только для предпросмотра.

**Нужно:** `logoId` в бренде — по образцу `fileId`/`creativeId` в договоре.

### 10. Нет счётчика кампаний у бренда

Карточка бренда показывает число его кампаний. В объекте `Advertiser` такого
поля нет, поэтому вариантов два, и оба плохие: спрашивать
`/campaigns?advertiserId=…&limit=1` на каждую карточку (девять запросов на
страницу) или тянуть все кампании и считать на клиенте. Сейчас выбран второй.

**Нужно:** `campaignsCount` в `Advertiser` (или агрегат `/campaigns/facets`
из `backend-spec.md` §12).

### 11. Нет поиска по брендам

`?q=` игнорируется — возвращается весь список:

```
GET /advertisers?q=Click&limit=100 → total: 9
```

У `/campaigns` параметр `q` есть. Пока брендов девять, фронт ищет локально,
но с ростом базы это перестанет работать вместе с пагинацией.

**Нужно:** `q` по названию, контактному лицу и категории, как у кампаний.

## Мелочи

### 12. На стенде работает только `admin`

Описание схемы обещает `admin/admin`, `viewer/viewer` и `adv/adv`, фактически
две последние учётки отвечают `401`. Причина видна в `/users`: в базе стенда
заведён один пользователь.

```
GET /users?limit=100 → {"items":[{"login":"admin", …}], "total": 1}
```

Роли `viewer` и `advertiser` мы проверить не смогли — а именно у них самые
сложные правила доступа.

### 13. У `admin` пустые `name` и `email`

```json
{ "id": 1, "role": "admin", "name": "", "email": "", "advertiserId": null }
```

Показывать в шапке нечего, поэтому фронт подставляет название роли.

### 14. Порядок выдачи не описан

Список отдаётся, судя по всему, по убыванию `createdAt`, но в схеме про
сортировку ничего нет и параметра `sort` не заявлено. Стоит зафиксировать
хотя бы в описании — от порядка зависит стабильность курсорной пагинации.

## Договоры

### 15. `GET /contracts` не похож на остальные списки

Все списки в API — курсорная пагинация `{items, nextCursor, total}`
с параметрами `limit` и `cursor`. Договоры отдаются голым массивом, а
параметры молча игнорируются:

```
GET /contracts                 → [ …18 объектов ]
GET /contracts?limit=1         → [ …те же 18 ]
GET /contracts?advertiserId=2  → [ …те же 18 ]
```

**Нужно:** привести список к общему виду — `{items, nextCursor, total}` плюс
`limit`, `cursor` и фильтр по бренду.

### 16. В договоре нет ссылки на бренд

В ответе `Contract` нет `advertiserId`, и по номеру бренд тоже не найти —
номера не уникальны (см. п. 3). То есть по плоскому списку нельзя показать,
чей это договор, а в интерфейсе рядом с каждым договором стоит карточка
бренда: название, логотип, цвет.

Из-за этого раздел «Договоры» читает не `/contracts`, а `/advertisers`, где
договоры приходят вложенными. Правятся они при этом по своему адресу —
`PATCH /contracts/:id`, и он работает как ожидается:

```
PATCH /contracts/16 {"status":"completed"} → 200
```

**Нужно:** `advertiserId` в `Contract` — тогда список договоров станет
самостоятельным и перестанет тянуть за собой всех рекламодателей.

### 17. `file` и `creative` в схеме появились, загрузки в интерфейсе ещё нет

Замечание 5 закрыто: поля описаны, на запись есть `fileId` и `creativeId`,
рядом появился `POST /files`. Фронт их пока не отправляет — сначала нужен
раздел загрузки файлов в форме. Оставляем как напоминание себе, не задачу
бэкенду.

## Кампании

### 18. Раздел нечем наполнить

Кампаний на стенде нет, а завести их некому:

```
GET /campaigns?limit=100 → {"items": [], "total": 0}
```

Заявку создаёт только рекламодатель — бренд сервер берёт из сессии автора
(`CampaignCreate`: «бренд берётся из сессии, а не из тела запроса»). Учётки
с ролью `advertiser` на стенде нет (см. п. 12), поэтому ни один сценарий
кампаний — список, фильтры по брендам и договорам, статистика месяца — на
живых данных проверить нельзя.

**Нужно:** учётка рекламодателя и несколько демо-кампаний в дев-базе.

### 19. Площадка не может завести заявку за бренд

Это следует из того же правила: у админа в сессии бренда нет, а `advertiserId`
на запись закрыт. Спека (§4.1) с этим согласна — «создаёт только
рекламодатель», — и мы убрали создание кампании из интерфейса площадки. Стоит
всё же решить сознательно: на практике заявку часто заводит менеджер по
телефонной просьбе клиента. Если такой сценарий нужен, потребуется
`advertiserId` в теле запроса для роли `admin`.

### 20. Ролик кампании упирается в ту же загрузку файлов

`creativeUrl` — ссылка не длиннее 500 символов, то есть выбранный файл
отправить некуда (та же история, что с логотипом бренда, п. 9). Пока в форме
кампании остаётся поле для ссылки. У договора для ролика есть `creativeId`
и `POST /files` — в кампании такого поля нет, ролик хранится ссылкой.

## Файлы

### 21. Загрузчик работает, но `Upload.file` описан как `uri`

В схеме `Upload` поле `file` объявлено строкой с `format: uri`, хотя
эндпоинт ждёт бинарник в multipart. Проверено запросом:

```
POST /files   (multipart: file=@dogovor.pdf, kind=contract)
→ 201 {"id":2,"name":"dogovor.pdf","url":"/api/v1/files/<slug>/download",
       "size":135,"mime":"application/pdf","addedAt":"…"}
```

Работает как надо, но генераторы клиентов по такой схеме сделают строковое
поле. **Нужно:** `type: string, format: binary`.

### 22. Скачивание файла закрыто токеном

`GET /files/<slug>/download` требует `Authorization`:

```
GET /files/<slug>/download                    → 401
GET /files/<slug>/download  (Bearer <access>) → 200, image/png
```

Из-за этого ссылку нельзя просто положить в `<a download>` или в `<img src>`:
браузер отправит запрос без заголовка и получит 401. Фронт обходит это —
тянет файл своим транспортом и отдаёт браузеру блобом, — но это лишний
проход через JS, и картинку так вообще не показать (логотип, превью ролика).

**Нужно:** отдавать файл по слагу без авторизации (slug и так неугадываемый —
64 символа) либо выдавать короткоживущую подписанную ссылку.

### 23. У ролика кампании нет `creativeId`

В договоре ролик подключается идентификатором (`creativeId`), а в кампании
осталось только `creativeUrl` — строка-URL не длиннее 500 символов. То есть
загрузить ролик прямо в кампанию нельзя, и ссылку на собственный загрузчик
туда тоже не положить (см. п. 22). Пока в форме кампании остаётся поле для
внешней ссылки.

**Нужно:** `creativeId` в кампании — как в договоре.
