# Бэкенд: состояние API и что нужно фронту

Стенд `https://setanta.pythonanywhere.com`, схема `/api/v1/schema`, фронт —
ветка `dev`. Каждый пункт проверен запросом; ответ сервера приведён.

Раздел «Площадки» (`/channels`) сознательно не трогаем: эндпоинты есть, экран
живёт на моке, подключим позже.

---

## 1. Что подключено

| Раздел      | Эндпоинты                                                                                                                                  |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| auth        | `login`, `logout`, `me`, `refresh` — с прозрачным обновлением истёкшего access                                                             |
| advertisers | список, создание, карточка, `PATCH`, удаление, смена статуса из плитки                                                                     |
| contracts   | `POST`/`PATCH`/`DELETE` внутри бренда, `PATCH /contracts/:id`, `amounts`, `payment-status`, `campaign-info`, правка и удаление поступлений |
| campaigns   | список, создание (рекламодателем), `PATCH`                                                                                                 |
| users       | список, создание, `PATCH`, удаление                                                                                                        |
| files       | `POST /files` для скана договора и ролика договора, скачивание по слагу через транспорт                                                    |

Кроме `channels`, в схеме не осталось неподключённых разделов.

---

## 3. Задачи бэкенду

По убыванию важности. Закрытые пункты оставлены в конце раздела — чтобы было
видно, что уже сделано.

### Блокирующее

#### 3.1 CORS не настроен

Preflight отвечает `200` без единого заголовка `Access-Control-Allow-*`, браузер
не пропускает ни один запрос. Фронт ходит через прокси (`server.proxy` в
разработке, `rewrites` на Vercel) — это обход: любой сторонний клиент упрётся
в то же самое.

**Нужно:** `django-cors-headers` с белым списком origin'ов фронта.

### Файлы

#### 3.2 Скачивание закрыто токеном

```
GET /files/<slug>/download                    → 401
GET /files/<slug>/download  (Bearer <access>) → 200
```

Ссылку нельзя положить ни в `<a download>`, ни в `<img src>` — браузер идёт
без заголовка. Фронт тянет файл транспортом и отдаёт блобом; картинку
(логотип, превью ролика) так не показать вовсе.

**Нужно:** отдавать файл по слагу без авторизации — он неугадываемый, 64
символа, — либо короткоживущая подписанная ссылка.

#### 3.3 `logoId` у бренда

`logo` принимает только абсолютный URL:

| Что отправили                   | Ответ                                      |
| ------------------------------- | ------------------------------------------ |
| `https://example.com/logo.png`  | `200`                                      |
| `/api/v1/files/<slug>/download` | `400` `{"logo":"Введите правильный URL."}` |
| `data:image/png;base64,…`       | `400`                                      |

Адрес собственного загрузчика относительный и к тому же закрыт токеном
(3.2). Поэтому логотип хранится ссылкой, а выбранный файл — только
предпросмотр.

**Нужно:** `logoId` — по образцу `fileId`/`creativeId` в договоре.

#### 3.4 `creativeId` у кампании

У договора ролик подключается идентификатором (`creativeId` + `campaign-info`),
у кампании такого поля нет — только `creativeUrl`, строка до 500 символов.

Обходим так: файл заливаем через `POST /files` с `kind=creative`, а в кампанию
кладём ссылку на него. Ссылка обязана быть абсолютной:

```
PATCH /campaigns/40 {"creativeUrl":"/api/v1/files/<slug>/download"}
→ 400 {"creativeUrl":"Введите правильный URL."}

PATCH /campaigns/40 {"creativeUrl":"https://<хост>/api/v1/files/<slug>/download"}
→ 200
```

Минусов у обхода два. Связи с файлом нет, поэтому сервер не проверит, что по
ссылке действительно ролик, и не уберёт файл вместе с кампанией. И ссылка
закрыта токеном (3.2): открыть её напрямую нельзя, фронт тянет ролик
транспортом и показывает блобом.

**Нужно:** `creativeId` в `Campaign`, как в договоре.

#### 3.5 `Upload.file` описан как `uri`

Эндпоинт ждёт бинарник в multipart и работает:

```
POST /files  (multipart: file=@dogovor.pdf, kind=contract)
→ 201 {"id":2,"name":"dogovor.pdf","url":"/api/v1/files/<slug>/download",…}
```

Но в схеме поле — строка с `format: uri`; генераторы клиентов сделают
строковое поле. **Нужно:** `type: string, format: binary`.

### Пользователи

#### 3.6 Имя, фамилия и телефон: `POST /users`, `PATCH /users/:id`

В карточке пользователя поля идут парами: имя и фамилия, email и телефон,
логин и роль, пароль и бренд, ниже доступ. В `ManagedUser` есть только `name`.

| Поле                    | Что нужно                                                                                                                                            |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `firstName`, `lastName` | строки, необязательные, `maxLength` 150. Сейчас фронт склеивает «Имя Фамилия» в `name` и делит обратно по первому пробелу — двойные фамилии ломаются |
| `phone`                 | строка, необязательная, `maxLength` 32, без жёсткой маски. В форме поле стоит, но заблокировано и не отправляется                                    |

Оба — на создание и правку, и в ответе списка `GET /users`: в таблице их
видно. `name` лучше оставить вычисляемым на сервере, чтобы не сломать
`GET /auth/me` и подпись в шапке.

### Договоры

#### 3.7 В договоре нет `advertiserId`

По плоскому `GET /contracts` не понять, чей договор, а по номеру бренд не
найти — номера не уникальны (3.9). Поэтому раздел «Договоры» читает
`/advertisers` с вложенными договорами, а правит их по своему адресу
(`PATCH /contracts/16 {"status":"completed"} → 200`).

**Нужно:** `advertiserId` в `Contract`.

#### 3.8 `GET /contracts` не похож на остальные списки

Отдаёт голый массив, `limit`, `cursor` и `advertiserId` игнорирует:

```
GET /contracts?limit=1         → [ …18 объектов ]
GET /contracts?advertiserId=2  → [ …те же 18 ]
```

**Нужно:** `{items, nextCursor, total}` плюс `limit`, `cursor` и фильтр по бренду.

#### 3.9 Номер договора не уникален

Спека (§2.3): «`number` — уникален по всей базе». Фактически
`POST /advertisers/3/contracts {"number":"Д-2026/1001"}` → `201`, хотя номер
уже был у другого бренда. Кампания ссылается на договор по номеру — дубликаты
делают выбор неоднозначным.

**Нужно:** `unique` на номер и `400` с полем `number` в `fields`.

#### 3.10 `paymentStatus` пустой строкой

В схеме поле обязательное и ограничено `PaymentStatusEnum` (`awaiting`/`paid`),
сервер отдаёт `""`. Клиенты по схеме на этом ломаются.

**Нужно:** пустое значение в enum (как `BlankEnum` у `package`) либо `null`
и `nullable`.

#### 3.11 `leagues` без типа

`Contract.leagues: {}` — по факту массив строк. Генераторы типов дают `any`.

### Кампании

#### 3.12 Площадка не может завести заявку за бренд

`CampaignCreate.advertiserId` только на чтение — бренд берётся из сессии
автора. Спека (§4.1) с этим согласна: «создаёт только рекламодатель», и
кнопка создания у админа убрана. Стоит решить сознательно: на практике заявку
часто заводит менеджер по звонку клиента.

**Если сценарий нужен:** `advertiserId` в теле запроса для роли `admin`.

### Общее

#### 3.13 Снимок условий договора у кампании пустой

`Campaign` объявляет `package`, `leagues`, `contractStart`, `contractEnd` как
снимок условий договора, но сервер их не заполняет:

```
GET /campaigns?limit=1
→ {"contractNumber":"Д-2026/101","package":"","leagues":[],
   "contractStart":null,"contractEnd":null,"legalName":"ООО «Artel»"}

GET /advertisers/1  → contracts[0]
→ {"number":"Д-2026/101","package":"general",
   "leagues":["laliga","bundesliga"],"start":"2026-06-01","end":"2026-08-01"}
```

Условия у договора есть, в кампанию они не переехали. Карточка кампании
из-за этого выглядит полупустой: пропадают плитки «Пакет», «Лиги» и «Срок
договора». Фронт сейчас добирает их из договора по номеру — обходной путь,
и он работает, только пока договор виден клиенту.

**Нужно:** заполнять снимок при создании заявки и при смене `contractNumber`.
Если снимок задуман только на момент создания — старые записи стоит
пересчитать разово.

#### 3.14 `version` и 409

Проверка работает, но только если поле прислать:

```
PATCH /advertisers/3 {"contact":"…","version":1} → 200, повторно → 409
PATCH /advertisers/3 {"contact":"…"}             → 200, без проверки
```

В схеме у `PATCH` только `200`. **Нужно:** описать `409` и решить, обязателен
ли `version`. Фронт его пока не шлёт — см. раздел 5.

#### 3.15 Выйти с истёкшим access нельзя

`POST /auth/logout` требует `Authorization`; с протухшим access — `401`,
refresh при этом живой. Клиент забывает токены локально, сессия на сервере
не погашена.

**Нужно:** пускать `/auth/logout` без `Authorization` — refresh в теле сам
доказывает владение сессией.

#### 3.16 Ошибки JWT нарушают собственный контракт

```json
{
  "error": {
    "code": "token_not_valid",
    "message": "Данный токен недействителен для любого типа токена",
    "fields": { "code": "token_not_valid", "messages": "AccessToken" }
  }
}
```

`fields` не про поля формы, `message` не для пользователя. **Нужно:** для 401
`fields` пустой, `message` человеческий («Сессия истекла, войдите заново»).
Обычная валидация оформлена правильно — с неё и брать пример.

#### 3.17 `campaignsCount` у бренда и поиск `?q`

Карточка бренда показывает число кампаний — поля нет, тянем все кампании и
считаем на клиенте. `GET /advertisers?q=Click` игнорируется (`total: 9`),
у `/campaigns` параметр есть. Пока брендов девять — терпимо, с ростом базы
перестанет работать вместе с пагинацией.

**Нужно:** `campaignsCount` в `Advertiser` (или `/campaigns/facets`) и `q` по
названию, контактному лицу и категории.

#### 3.18 Порядок выдачи не описан

Списки идут, судя по всему, по убыванию `createdAt`, но в схеме ни слова и
параметра `sort` нет. Зафиксировать хотя бы в описании — от порядка зависит
стабильность курсорной пагинации.

#### 3.19 У `admin` пустые `name` и `email`

Мелочь: в шапке показывать нечего, фронт подставляет название роли.

### Закрыто

- **Загрузка файлов появилась** — `POST /files`, `fileId` и `creativeId` в
  договоре описаны и подключены. Осталось 3.2–3.5.
- **Учётки на стенде** — есть `viewer`, `cola` (Coca Cola) и `artel` (Artel).
  Роли `advertiser` проверена вживую; `viewer` — ещё нет, см. 5.
- **Демо-данные** — 40 кампаний по двум брендам, залиты нашими сидерами
  (`scripts/seed-mock-campaigns.mjs`).

## 4. Чего нет вообще: разделы на моке

Данные лежат в `src/lib/*Seed.js` и правятся в localStorage; форматы описаны
по факту того, что рисует интерфейс.

### 4.1 Обзор — помесячный отчёт площадки

Экран `/app/overview`. Один документ на месяц, админ правит его прямо на
странице, viewer только смотрит.

```
GET   /overview?period=2026-08     → OverviewReport
PUT   /overview/2026-08            → OverviewReport   (admin)
```

| Блок                    | Поля                                                                                   |
| ----------------------- | -------------------------------------------------------------------------------------- |
| `summary`               | заголовок, подзаголовок, число публикаций, охват в соцсетях                            |
| `mediaTotals[]`         | прямые эфиры, рекламные ролики, промо в эфире, хронометраж (сек.), просмотры Live Ads  |
| `socialChannels[]`      | канал (Instagram / Telegram), число публикаций, суммарный охват, охваты по публикациям |
| `audience`              | доля мужчин, заголовок и примечание к возрастной структуре                             |
| `ageShare[]`            | доли возрастных групп 13–17 / 18–24 / 25–34 / 35–44 / 45–54                            |
| `deviceShare[]`         | доли устройств: браузер, Smart TV, телефон, планшет                                    |
| `platformDeviceShare[]` | то же в разрезе OTT и TV                                                               |
| `leagueAgeRows[]`       | вид спорта, перечень лиг, распределение по четырём возрастным группам                  |

Цвета и иконки — забота фронта, в API не нужны. Источник: `src/lib/overviewSeed.js`.

### 4.2 Отчёты по кампании и договору

Экраны: статистика кампании (`/app/campaigns/:id`) и «Отчёт» у рекламодателя.
Отчёт привязан к **договору и месяцу**.

```
GET /reports/spot?contract=Д-2026/901&period=2026-08
```

- **Total statistic** — сводка по двум телеканалам: ролики, хронометраж, просмотры Live Ads, промо, OTT pre-roll.
- **Spot statistic** — то же в разрезе Setanta Sports 1 и 2: standard spot и live spot (UFC / Football), в штуках и секундах.
- **Лог выходов** — построчно: ролик, дата, время (GMT+4), канал. Выгрузка из «Шаблона импортируемого отчёта Setanta Statistics».
- **Промо** — тот же лог по промо-выходам.
- **Соцсети** — публикации Instagram и Telegram с охватами.
- **OTT** — live spot и pre-roll: показы и просмотры.
- **Медиаплан** — план размещения, редактируемая таблица.

Формат строк: `{ item, date, time, channel }` для логов, `{ label, value }` для
сводок. Если данные приходят выгрузкой из внешней системы — удобнее эндпоинт
загрузки файла отчёта плюс чтение по договору и месяцу. Формат лучше
обсудить до реализации: это самый большой кусок.

### 4.3 Динамика по дням для графика кампании

График за 14 дней (расход, показы, клики) сейчас генерируется на клиенте из
итоговых чисел — то есть выдуман.

```
GET /campaigns/:id/timeseries?metric=impressions&from=…&to=…  → [{ date, value }]
```

Если такого разреза в системе нет — скажите, график уберём.

### 4.4 Пользовательские вкладки и таблицы отчёта

Состав вкладок отчёта, загруженные таблицы спот-логов и правки сводок живут
в localStorage браузера — у каждого человека свои. Если это общие данные,
нужен серверный аналог: состав вкладок и содержимое таблиц по договору.

## 6. Порядок, который предлагаем

1. CORS — без него всё работает только через прокси.
2. Файлы: скачивание без токена, `logoId`, `creativeId`, схема `binary`.
3. Пользователи: `firstName`, `lastName`, `phone`.
4. Договоры: `advertiserId`, пагинация `/contracts`, уникальность номера, `paymentStatus`.
5. `version`/409 и logout — общие правила, которые потом тяжело менять.
6. Обзор — самый заметный раздел на моке.
7. Отчёты и логи выходов — самый большой кусок, формат обсудить заранее.
