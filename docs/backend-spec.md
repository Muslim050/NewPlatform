# Setanta Sports Platform — задача для бэкенда

Документ описывает, что должен реализовать бэкенд, чтобы фронт перестал жить на моках.
Фронт готов и работает: React 18 + Vite, SPA, все данные сейчас в `localStorage`.

**Что заменяем на API:**

| Что сейчас | Где в коде | Чем станет |
|---|---|---|
| Вход по хардкоду `admin/admin`, `viewer/viewer`, `adv/adv` | `src/pages/Login.jsx`, `src/context/AuthContext.jsx` | авторизация с токеном |
| Вся база (бренды, площадки, кампании) в одном ключе `bloom.db.v12` | `src/lib/store.js`, `src/context/DataContext.jsx` | REST |
| Медиапланы Live Spot | `src/components/campaigns/CampaignMediaTabs.jsx`, ключ `setanta.campaign.live-spots.v4` | REST |
| Логи выходов (SS1/SS2 UZB, Event Promo) | `src/components/campaigns/SpotLogTable.jsx`, ключ `setanta.campaign.spot-logs.v1` | REST |
| Файлы (договор, ролик) как base64 в базе | `src/components/ui/FilePicker.jsx` | загрузка в хранилище |

Начальные данные лежат в `src/lib/seed.js` — их удобно взять как фикстуры для дев-окружения.

## 1. Роли и доступ

Три роли: **admin** (сотрудник площадки), **viewer** (тот же админский обзор, но без права
что-либо менять) и **advertiser** (бренд). У рекламодателя в профиле есть `advertiserId` —
он видит только свои данные.

| Раздел | admin | viewer | advertiser |
|---|---|---|---|
| Кампании (список, карточка) | все | все | только своего бренда |
| Создание кампании | — | — | да |
| Редактирование кампании, смена статуса | да | нет | нет |
| Суммы: правка «к оплате / оплачено», внесение поступления | да | нет | нет |
| Суммы: просмотр «Бюджет / Оплачено» и истории выплат | да | да | да |
| Рекламодатели, их договоры и реквизиты | правит | только читает | нет |
| Площадки (`/app/channels`) | правит | только читает | читает |
| Обзор (`/app/overview`) | да | да | нет |
| Отчёт (`/app/reports`) | нет | нет | да |
| Медиаплан и логи выходов | правит и импортирует | читает и выгружает | только читает |

Фильтрация «своих» кампаний обязательна на сервере, а не только на клиенте
(сейчас это делает `src/lib/useScope.js`). Права на запись тоже проверяются на сервере:
`viewer` не должен проходить ни один мутирующий эндпоинт, `advertiser` — только создание
своей кампании.

На фронте это единый флаг `canEdit` в `src/context/AuthContext.jsx`; `isAdmin` там истинен
и для `viewer`, потому что состав экранов у них одинаковый.

шапке статистики и в профиле рекламодателя. Сейчас это либо путь к файлу в `/public/logos`,
либо `data:`-URL загруженного файла; на бэке — ссылка из хранилища (см. §6). Пустое значение
допустимо, фронт нарисует инициалы на фирменном цвете (`src/components/ui/Avatar.jsx`).

### 2.3 Contract (договор бренда)

Договоры принадлежат бренду; кампания ссылается на договор по номеру.

| Поле | Тип | Комментарий |
|---|---|---|
| `id` | uuid | |
| `advertiserId` | uuid | |
| `number` | string | уникален **по всей базе**, обязателен |
| `campaignName` | string | название рекламной кампании, под которую заключён договор |
| `legalName` | string | подставляется из карточки бренда, в форме договора не спрашивается |
| `package` | `partner` \| `general` \| `presenter` | |
| `leagues` | string[] | коды лиг |
| `start`, `end` | date | срок договора |
| `paymentDate` | date | сроки оплаты; в форме договора не редактируется |
| `file` | `{ name, url }` \| null | скан договора |
| `creative` | `{ name, url }` \| null | рекламный ролик договора |

`campaignName` и `creative` — новые поля. В форме кампании рекламодатель сначала выбирает
номер договора, затем рекламную кампанию этого договора; вместе с выбранной кампанией в форму
подставляется её ролик (`creative` → `creativeUrl` / `creativeName` кампании).

## 3. Справочники

**Статусы кампании** (`src/lib/metrics.js`):

| Код | Подпись | Смысл |
|---|---|---|
| `sent` | Отправлен | заявку создал рекламодатель |
| `received` | Получен | площадка приняла в работу |
| `reviewing` | Рассматривается | на согласовании |
| `active` | Активен | идёт размещение |
| `completed` | Завершен | закончилась |
| `awaiting_payment` | Ожидает оплату | отработала, деньги ещё не пришли |

Порядок в воронке — как в таблице; сортировка списка идёт по нему. `awaiting_payment` —
новый статус, идёт после «Завершен»; в интерфейсе выделен красным и пульсирует.

**Пакеты:** `partner` — Партнёр, `general` — Генеральный спонсор, `presenter` — Презентер.

**Лиги:** `epl`, `laliga`, `bundesliga`, `ligue1`, `seriea`, `ufc`, `f1`, `atp`, `wta`,
`zuffa`, `nba`, `nhl`.

**Статусы бренда:** `active`, `paused`. **Статусы площадки:** `active`, `inactive`.

## 4. Бизнес-правила

1. **Создание кампании.** Создаёт только рекламодатель, статус всегда `sent`. Обязательны
   название (оно же — рекламная кампания из договора) и период. Бюджет при создании = 0 —
   его проставляет площадка.
2. **Смена статуса.** Только admin, вручную, любым переходом (жёсткого автомата нет).
   Проверять, что статус из списка.
3. **Редактирование.** Admin правит кампанию в любом статусе, включая `active` и `completed`
   (ограничение снято). Рекламодатель после отправки заявку не редактирует.
4. **Удаление кампаний** в UI отключено, эндпоинт можно не делать.
5. **Договор.** При выборе номера договора в кампанию копируются пакет, лиги, юр. лицо и
   срок; при выборе рекламной кампании этого договора — её ролик. Дальше это снимок: правка
   договора бренда не меняет существующие кампании. Если у бренда договоров нет — номер
   вводится вручную.
6. **Что рекламодатель не редактирует в форме кампании.** Срок договора подставляется из
   договора и заблокирован, поле юр. лица скрыто, файл договора доступен только на скачивание,
   подставленный ролик нельзя удалить (заменить своим — можно).
7. **Деньги.** `budget` — сколько бренд должен заплатить, `spent` — сколько оплатил.
   Поступление вносится с суммой и датой-временем, прибавляется к `spent` и попадает в
   историю выплат. Рекламодатель и viewer видят суммы и историю, но не правят их.
8. **Уникальность номера договора** — по всей базе, а не только внутри бренда: иначе один
   номер всплывает у двух брендов и путает выбор в форме кампании.
9. **Удаление бренда** не удаляет его кампании — они остаются без привязки; UI
   предупреждает об этом.
10. **Счётчики.** На вкладках брендов показывается число кампаний, количество заявок в
    статусе `sent` (синяя метка) и количество активных (зелёная). Вкладки статусов с нулевым
    счётчиком в фильтрах не показываются.
11. **Процент на статусе** — это доля пройденного срока кампании
    (`timeProgress` в `src/lib/metrics.js`), а не освоение бюджета. Освоение показывает
    полоса в колонке «Бюджет / Оплачено» — `spent / budget`.

## 5. API

Базовый префикс `/api/v1`. Ответы — JSON, ошибки — `{ "error": { "code", "message", "fields": {} } }`.

### Аутентификация
```
POST   /auth/login          { login, password } → { token, user }
POST   /auth/logout
GET    /auth/me             → { user }
```
`user` — `{ id, role, name, email, advertiserId }`.

### Рекламодатели
```
GET    /advertisers                    (admin) список с contracts и requisites
POST   /advertisers                    (admin)
GET    /advertisers/:id
PATCH  /advertisers/:id                (admin)
DELETE /advertisers/:id                (admin)
```
Договоры приходят и сохраняются вместе с брендом (форма правит их одним списком).
Если удобнее — отдельные `POST/PATCH/DELETE /advertisers/:id/contracts/:contractId`,
фронт подстроится.

### Площадки
```
GET    /channels
POST   /channels                       (admin)
PATCH  /channels/:id                   (admin)
DELETE /channels/:id                   (admin)
```

### Кампании
```
GET    /campaigns?advertiserId=&status=&contractNumber=&q=
GET    /campaigns/:id
POST   /campaigns                      (advertiser)
PATCH  /campaigns/:id                  (admin)
```
Для роли `advertiser` сервер сам ограничивает выдачу его брендом, независимо от параметров.

Отдельно для сумм — чтобы не гонять всю кампанию:
```
PATCH  /campaigns/:id/amounts          (admin) { budget?, spent? }
GET    /campaigns/:id/payments          история выплат, все роли
POST   /campaigns/:id/payments         (admin) { amount, paidAt }
PATCH  /campaigns/:id/payments/:payId  (admin) { paidAt }
```
Поступление прибавляется к `spent`, дату и время задаёт пользователь. Ответ — обновлённая
кампания вместе с историей. Правка даты уже внесённой выплаты нужна: в интерфейсе она
редактируется прямо в списке.

### Медиаплан и логи выходов
```
GET    /campaigns/:id/media-plan/:tab           tab = spot1 | spot2
PUT    /campaigns/:id/media-plan/:tab           { rows: [...] }   (admin) — сохранение целиком
GET    /campaigns/:id/logs/:tab                 tab = ss1uzb | ss2uzb | promo1 | promo2
PUT    /campaigns/:id/logs/:tab                 { rows: [...] }   (admin)
```
Фронт правит таблицу целиком и сохраняет по кнопке — `PUT` со всем списком строк
проще всего и совпадает с текущим поведением.

### Файлы
```
POST   /files                          multipart → { id, name, url, size, mime }
```
Используется для скана договора, рекламного ролика и логотипа бренда. В сущностях храним
`{ name, url }`, у бренда — только `url`.

### Аналитика
```
GET    /campaigns/:id/timeseries?metric=spent|impressions|clicks&days=14
GET    /campaigns/:id/report                    сводка по каналам, гео, устройствам, соцсетям
GET    /overview                                (admin) сводка для страницы «Обзор»
GET    /reports/summary                         (advertiser) для страницы «Отчёт»
```

## 6. Файлы

- Сейчас файлы кладутся в базу как `data:`-URL с лимитом 2 МБ, крупные держатся
  на `blob:`-ссылке до перезагрузки. Это заглушка.
- Нужно: загрузка в S3-совместимое хранилище, отдача по ссылке, ограничение типов
  (`.pdf/.doc/.docx/изображения` для договора, `video/*` для ролика, `image/*` для логотипа)
  и размера.
- Ссылка на ролик может быть и внешней (`http(s)`) — фронт это допускает.
- Скачивание: договор качается из карточки кампании (плитка «Номер договора»), из формы
  договора и из формы кампании у рекламодателя; ролик — из формы договора. Ссылка должна
  отдаваться с именем файла, чтобы `download` сохранял его читаемо.

## 7. Импорт и экспорт Excel

Разбор и сборка `.xlsx` сейчас делаются на клиенте (`src/lib/xlsx.js`, зависимость `fflate`).
Если оставляем так — от бэкенда нужно только сохранение строк. Если переносим на сервер —
вот что должен уметь парсер.

**Медиаплан (Live Spot).** Заголовки распознаются по названиям: `Дата`, `Время GMT+4`,
`Турнир`, `Событие`, `Канал`, `Pre`, `Mid 1`, `Mid 2`, `Post`, `Просмотры` (и англоварианты).
Если строки заголовков нет — колонки читаются по порядку. Пустые строки отбрасываются.

**Логи выходов.** Файл клиента (`Пример_Report_JANUARY 2026.xlsx`) содержит четыре листа,
каждая вкладка берёт свой:

| Вкладка | Лист |
|---|---|
| `ss1uzb` | `SS1 UZB` |
| `ss2uzb` | `SS2 UZB` |
| `promo1` | `Event Promo SS 1` |
| `promo2` | `Event Promo SS2` |

Имя листа сопоставляется без учёта пробелов и регистра. Шапка файла (название бренда,
пустые строки) пропускается, данные читаются после строки `ITEM NAME | DATE | TIME`.

**Форматы значений.** В одних листах время текстом (`19:09:13`), в других — числом-долей
суток (`0.578136…` → `13:52:31`). Даты могут прийти порядковым номером дня Excel
(отсчёт от 30.12.1899) — разворачиваются в `дд.мм.гггг`.

**Экспорт.** Кнопка «Скачать» собирает `.xlsx` из текущей таблицы (лист называется как
вкладка, первая строка — заголовки).

## 8. Метрики

Формулы уже зафиксированы в `src/lib/metrics.js`, повторить один в один:

```
ctr    = impressions ? clicks / impressions * 100 : 0
cvr    = clicks ? conversions / clicks * 100 : 0
cpa    = conversions ? spent / conversions : 0
cpm    = impressions ? spent / impressions * 1000 : 0
pacing = budget ? spent / budget * 100 : 0
```

Агрегаты по списку кампаний: суммы `budget`, `spent`, `impressions`, `clicks`,
`conversions`, плюс `ctr`, `cvr`, `cpa` от сумм и количество активных.

**Что сейчас захардкожено во фронте и должно приехать с бэка:**

- страница «Обзор» — `src/pages/Dashboard.jsx` (медиапоказатели, соцсети, гео, устройства);
- отчётные панели кампании — `src/components/campaigns/CampaignReportPanels.jsx`
  (Total Spot statistic, Social media, Total statistics, список городов);
- графики динамики на странице статистики — генерируются функцией `seededSeries`
  (`src/lib/id.js`), то есть это псевдослучайные числа, а не данные.

## 9. На что обратить внимание при переносе

1. **`createdAt` с временем.** Подсказка на статусе показывает дату и время отправки заявки —
   если сохранять только дату, время пропадёт.
2. **Формат дат.** Фронт везде выводит `дд.мм.гггг`, API удобнее отдавать ISO (`2026-08-31`)
   и `datetime` в ISO 8601 — форматирование на клиенте.
3. **Числа** передавать числами, не строками: суммы, охваты, метрики.
4. **Порядок строк** в медиаплане и логах важен — либо сохранять `position`, либо
   гарантировать порядок массива.
5. **Миграции в `src/lib/store.js`** (донабивка юр. лиц, договоров, статусов) — костыли мока,
   переносить не нужно.
6. **Точки интеграции на фронте:** `src/lib/store.js` и `src/context/DataContext.jsx` —
   там сейчас `create / update / remove / getState / subscribe`. Достаточно заменить их
   реализацию на HTTP-вызовы, компоненты трогать не придётся.

## 10. Что заложить в архитектуру сразу

Это не фичи, а решения, которые дорого менять потом.

**Пагинация и сортировка.** Кампаний будет сотни, строк логов — тысячи (месяц выходов
на четыре вкладки ≈ 2400 строк). Договориться о формате сразу:

```
GET /campaigns?limit=50&cursor=...&sort=-createdAt
→ { "items": [...], "nextCursor": "...", "total": 128 }
```

**Конкурентная правка.** Суммы кампании правит площадка, статус — тоже; два менеджера
легко перетрут друг друга. Нужна оптимистичная блокировка: отдавать `version` (или
`updatedAt`) и отклонять `PATCH` со старым значением, чтобы фронт показал «данные
изменились, обновите».

**Идемпотентность платежей.** «Поступление» прибавляет сумму — повторный запрос при
разрыве связи задвоит деньги. Принимать `Idempotency-Key` и игнорировать повтор.

**Аудит.** Кто менял статус, суммы, условия договора — писать в отдельную таблицу
(`entity`, `entityId`, `field`, `old`, `new`, `userId`, `at`). Для денег и договоров это
обязательное требование, а не удобство.

**Мягкое удаление.** Бренд удаляется, а его кампании остаются — при жёстком `DELETE`
история платежей и отчёты повиснут на несуществующем `advertiserId`. Лучше `deletedAt`.

**Формат ошибок и валидации.** Фронт умеет показывать ошибки под конкретными полями —
возвращать `{ error: { code, message, fields: { name: "Укажите название" } } }`, а не
просто 400.

**Хранение денег.** Суммы в узбекских сумах доходят до сотен миллионов — целые числа
(минорные единицы) или `numeric`, не `float`.

**Часовые пояса.** Медиаплан подписан «Время GMT+4» — хранить `timestamptz`, а не
локальные строки, иначе выходы поедут.

**i18n-готовность.** Справочники (статусы, пакеты, лиги, категории) отдавать кодами,
подписи держать на клиенте — иначе перевод на узбекский упрётся в базу.

## 11. Задел на будущее — что просят добавить

Порядок примерно по соотношению «польза / стоимость». Каждый пункт — это, по сути,
таблица плюс пара эндпоинтов; заложить структуру лучше сразу, реализовывать можно позже.

### 11.1 Акт сверки по бренду
История выплат на фронте уже есть (см. 2.8), но только внутри кампании. Для бухгалтерии
нужен свод по бренду и договору:

```
GET /advertisers/:id/payments?contractNumber=&from=&to=
```
Плюс поля, которых во фронте пока нет и которые дешевле завести сразу:
`comment`, `createdBy` (кто внёс), привязка к `contractNumber`.

### 11.2 Статистика из загруженных логов
Самое ценное по соотношению польза/затраты: клиент **уже** грузит реальные выходы в
`SS1/SS2 UZB` и `Event Promo`, а «Total statistics» и графики нарисованы константами.

Из строк лога (`item`, `date`, `time`) считаются: количество выходов за период,
разбивка по дням и по каналам, хронометраж (из медиаплана — `pre/mid1/mid2/post`),
просмотры. Эндпоинты `/campaigns/:id/timeseries` и `/campaigns/:id/report` из раздела 5
должны отдавать именно это, а не заглушки.

### 11.3 Уведомления
Событий уже хватает: пришла заявка (`sent`), сменился статус, приближается `paymentDate`,
заканчивается договор или период кампании.

```
Notification: id, userId, type, payload, readAt, createdAt
GET   /notifications?unread=true
POST  /notifications/:id/read
```
Плюс доставка наружу — email и/или Telegram. Колокольчик в шапке фронта пока декоративный,
под это и делался.

### 11.4 Комментарии к кампании
Сейчас после отправки заявки диалога нет: площадка не может попросить заменить ролик,
рекламодатель — уточнить статус. Всё уходит в мессенджеры.

```
Comment: id, campaignId, authorId, text, attachments[], createdAt
GET/POST /campaigns/:id/comments
```
Хорошо ложится вместе с аудитом: смена статуса пишется в ту же ленту системным сообщением.

### 11.5 Несколько пользователей на бренд
Один логин на компанию — это пароль, который пересылают в чате. Нужны связь
`user ↔ advertiser` многие-к-одному, приглашение по email, сброс пароля, отзыв доступа.

### 11.6 Дубликат кампании
`POST /campaigns/:id/duplicate` — копия с новым `id`, статусом `sent`, обнулёнными
метриками и суммами. Кампании повторяются сезонно, а форма длинная.

### 11.7 Сборка отчёта одним файлом
`GET /campaigns/:id/report.xlsx` — медиаплан, логи выходов и итоги в одной книге.
Рекламодателю есть что переслать своему клиенту. Экспорт из отдельных таблиц на фронте
уже написан (`src/lib/xlsx.js`), серверная сборка нужна для «всё сразу» и для писем.

### 11.8 Связность данных
Проверки, которых на сервере пока нет:
- номер договора уникален по всей базе (на фронте проверка уже есть, но она клиентская);
- период кампании укладывается в срок выбранного договора;
- `paymentDate` не раньше начала кампании;
- сумма поступлений не превышает `budget` (или явное разрешение переплаты);
- нельзя удалить договор, на который ссылаются кампании (или отвязывать явно).

## 12. Открытые вопросы

1. **Комментарий и автор у поступления.** В UI вносятся только сумма и дата — нужны ли
   комментарий, привязка к договору и `createdBy` для акта сверки?
2. **Переход в `awaiting_payment`** — ставится вручную или автоматически, когда кампания
   завершилась, а `spent < budget`?
3. **Смена статуса кампании** — свободные переходы или строгий автомат
   (`sent → received → reviewing → active → completed → awaiting_payment`)?
4. **Права рекламодателя на правку.** Сейчас после отправки он не может изменить заявку —
   оставляем так или разрешаем правку, пока статус `sent`?
5. **Площадки (`/app/channels`)** скрыты из меню, но страница работает. Нужны ли они в проде?
6. **Категории брендов** — фиксированный справочник или произвольный текст?
7. **Медиапланы и логи** — хранить по кампании (как предложено) или по договору/месяцу?
   Сейчас фронт показывает их как отчёт за выбранный месяц договора, см. §13.
8. **Реквизиты бренда** — оставляем свободным текстом или возвращаем структуру полей
   (ИНН, банк, счёт), чтобы подставлять их в документы?
9. **Несколько рекламных кампаний на договор.** Сейчас в договоре одно поле `campaignName`,
   и в форме кампании выбор из одного значения. Если кампаний по договору бывает несколько —
   нужен список, а не строка.
10. **Мультиязычность** интерфейса — сейчас только русский, влияет на формат дат и подписи.

## 13. Навигация по кампаниям — что за фильтры на экране

Порядок фильтров: **бренд → договор → месяц**. Это влияет на то, какие выборки нужны с сервера.

- **Вкладки брендов** — только бренды, у которых есть кампании; счётчики: всего, новых
  заявок (`sent`), активных.
- **Вкладки договоров** появляются, когда выбран бренд; счётчик — число кампаний по договору.
  Повторный клик снимает фильтр. Смена бренда сбрасывает выбранный договор и период.
- **Месяцы** появляются, когда выбран договор. Месяц отбирает кампании, чей период
  пересекается с ним; будущие месяцы недоступны.
  - **текущий месяц** — показывается таблица кампаний;
  - **закрытый месяц** — вместо таблицы открывается отчёт (медиаплан и логи выходов).
- **Статусы** — сегментные вкладки со счётчиками; вкладки с нулём скрываются.

Для сервера это означает как минимум фильтры `advertiserId`, `contractNumber`,
`period` (месяц/диапазон) и агрегаты для счётчиков — лучше отдавать их отдельным
эндпоинтом (`GET /campaigns/facets?...`), чтобы не тянуть весь список ради цифр.
