# Что фронту нужно от бэкенда

Сверено со схемой `https://setanta.pythonanywhere.com/api/v1/schema` и с кодом
ветки `dev`. Отдельно от `backend-feedback.md`: там замечания к тому, что уже
работает, здесь — список задач.

Раздел «Площадки» (`/channels`) сознательно не трогаем: эндпоинты есть, экран
живёт на моке, подключим позже.

---

## 1. Что уже подключено

| Раздел      | Эндпоинты                                                                                                                                  |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| auth        | `login`, `logout`, `me`, `refresh` — с прозрачным обновлением истёкшего access                                                             |
| advertisers | список, создание, карточка, `PATCH`, удаление                                                                                              |
| contracts   | `POST`/`PATCH`/`DELETE` внутри бренда, `PATCH /contracts/:id`, `amounts`, `payment-status`, `campaign-info`, правка и удаление поступлений |
| campaigns   | список, создание, `PATCH`                                                                                                                  |
| users       | список, создание, `PATCH`, удаление                                                                                                        |
| files       | `POST /files`, скачивание по слагу                                                                                                         |

Кроме `channels`, из схемы не осталось ничего неподключённого.

## 2. Эндпоинты, которые фронт не зовёт

Не претензия — просто чтобы вы знали, что они не в бою и их поведение мы
не проверяли.

| Эндпоинт                                   | Почему не зовём                                                                    |
| ------------------------------------------ | ---------------------------------------------------------------------------------- |
| `GET /contracts`, `GET /contracts/:id`     | договоры приходят вложенными в бренд; плоский список бесполезен (п. 16 в feedback) |
| `POST /contracts`, `DELETE /contracts/:id` | договор заводится и удаляется внутри бренда                                        |
| `GET /advertisers/:id/contracts`           | то же — список уже в карточке бренда                                               |
| `GET /contracts/:id/payments`              | поступления приходят внутри договора                                               |
| `POST /contracts/:id/payments`             | поступление создаётся приростом «Оплачено» через `amounts`                         |
| `GET /contracts/:id/status-log`            | история статусов приходит внутри договора (`paymentLog`)                           |
| `GET /campaigns/:id`, `GET /users/:id`     | карточки берём из списка                                                           |
| все `PUT`                                  | шлём `PATCH` — отправлять объект целиком незачем                                   |

Если их никто больше не использует, часть можно убрать из схемы: меньше
поверхности — меньше расхождений.

## 3. Правки в том, что уже есть

По убыванию важности. Подробности и запросы-доказательства — в
`backend-feedback.md`, номера пунктов в скобках.

1. **CORS** (п. 1) — заголовков нет вообще, фронт ходит через прокси. Единственное блокирующее.
2. **Скачивание файлов закрыто токеном** (п. 22) — `<img src>` и `<a download>` получают 401. Нужен доступ по слагу без авторизации либо подписанная ссылка. Сейчас фронт тянет файл через JS и отдаёт блобом; картинку так не показать вовсе.
3. **`logoId` у бренда** (п. 9) — логотип принимает только абсолютный URL, а загрузчик отдаёт относительный. Нужно поле по образцу `fileId` в договоре.
4. **`creativeId` у кампании** (п. 23) — ролик кампании остался строкой-ссылкой, загрузить файл некуда.
5. **`advertiserId` в `Contract`** (п. 16) — без него список договоров не показать рядом с брендом.
6. **Пагинация `GET /contracts`** (п. 15) — отдаёт голый массив, `limit` и `cursor` игнорирует.
7. **Уникальность номера договора** (п. 3) — дубликаты создаются, а кампания ссылается на договор по номеру.
8. **`paymentStatus` пустой строкой** (п. 4) — не входит в собственный enum; нужен `null` либо `BlankEnum`.
9. **`version` и 409** (п. 6) — без поля проверка не выполняется, правки молча затирают чужие. Решить, обязателен ли он.
10. **`Upload.file` описан как `uri`** (п. 21) — по факту принимает бинарник; нужен `format: binary`.
11. **`campaignsCount` в бренде** (п. 10) и **поиск `?q` по брендам** (п. 11) — сейчас тянем все кампании и фильтруем на клиенте.
12. **Учётки `viewer` и `advertiser` на стенде** (п. 12, 18) — роль `viewer` не проверена ни разу, кампании создавать некому.

## 4. Чего нет вообще: разделы на моке

Ниже — то, ради чего нужны новые методы. Данные сейчас лежат в
`src/lib/*Seed.js` и правятся в localStorage; форматы описаны по факту того,
что рисует интерфейс.

### 4.1 Обзор — помесячный отчёт площадки

Экран `/app/overview`. Один документ на месяц, админ правит его прямо на
странице (кнопка «Редактировать»), viewer только смотрит.

```
GET   /overview?period=2026-08     → OverviewReport
PUT   /overview/2026-08            → OverviewReport   (admin)
```

Состав `OverviewReport` (см. `src/lib/overviewSeed.js`):

| Блок                    | Поля                                                                                   |
| ----------------------- | -------------------------------------------------------------------------------------- |
| `summary`               | заголовок, подзаголовок, число публикаций, охват в соцсетях                            |
| `mediaTotals[]`         | прямые эфиры, рекламные ролики, промо в эфире, хронометраж (сек.), просмотры Live Ads  |
| `socialChannels[]`      | канал (Instagram / Telegram), число публикаций, суммарный охват, охваты по публикациям |
| `audience`              | доля мужчин, заголовок и примечание к возрастной структуре                             |
| `ageShare[]`            | доли возрастных групп 13–17 / 18–24 / 25–34 / 35–44 / 45–54                            |
| `deviceShare[]`         | доли устройств: браузер, Smart TV, телефон, планшет                                    |
| `platformDeviceShare[]` | то же в разрезе OTT и TV                                                               |
| `leagueAgeRows[]`       | вид спорта, перечень лиг, распределение по четырём возрастным группам                  |

Цвета и иконки — забота фронта, в API не нужны.

### 4.2 Отчёты по кампании и договору

Экраны: статистика кампании (`/app/campaigns/:id`) и «Отчёт» у рекламодателя.
Вкладки берутся из `src/components/campaigns/CampaignMediaTabs.jsx`, данные —
из `spotLogSeed.js` и `liveSpotSeed.js`. Отчёт привязан к **договору и месяцу**
(в интерфейсе он открывается из выбранного месяца договора).

```
GET /reports/spot?contract=Д-2026/901&period=2026-08
```

Что показывается:

- **Total statistic** — сводка по двум телеканалам: количество роликов, хронометраж, просмотры Live Ads, промо в эфире, OTT pre-roll.
- **Spot statistic** — то же в разрезе каналов Setanta Sports 1 и 2: standard spot и live spot (UFC / Football) отдельно, в штуках и секундах.
- **Лог выходов** — построчно: наименование ролика, дата, время (GMT+4), канал (SS1 / SS2). Это выгрузка из «Шаблона импортируемого отчёта Setanta Statistics», сейчас в моке 50 строк.
- **Промо** — тот же лог, но по промо-выходам, тоже с разбивкой по каналам.
- **Соцсети** — публикации Instagram и Telegram с охватами.
- **OTT** — live spot и pre-roll: показы и просмотры.
- **Медиаплан** — план размещения; в моке это редактируемая таблица.

Формат строк везде одинаковый: `{ item, date, time, channel }` для логов и
`{ label, value }` для сводок. Если данные приходят выгрузкой из внешней
системы, удобнее всего эндпоинт загрузки файла отчёта плюс чтение по договору
и месяцу.

### 4.3 Динамика по дням для графика кампании

На странице статистики есть график за 14 дней (расход, показы, клики). Сейчас
ряд генерируется на клиенте из итоговых чисел кампании.

```
GET /campaigns/:id/timeseries?metric=impressions&from=…&to=…
    → [{ date, value }]
```

Если такого разреза в системе нет — скажите, уберём график, чтобы не рисовать
выдуманное.

### 4.4 Медиаплан и пользовательские вкладки

В отчёте кампании можно завести свои вкладки (сохраняются в localStorage
браузера). Если это нужно всем, а не одному человеку за одним компьютером —
понадобится хранение на сервере: список вкладок и их содержимое по договору.

## 5. Порядок, который предлагаем

1. CORS — без него всё остальное работает только через прокси.
2. Файлы: скачивание без токена, `logoId`, `creativeId`.
3. Демо-данные и учётки `viewer` / `advertiser` на стенде — без них половину логики нельзя проверить.
4. Мелкие правки схемы: `advertiserId` в договоре, пагинация `/contracts`, `paymentStatus`, `version`.
5. Обзор — самый заметный раздел на моке.
6. Отчёты и логи выходов — самый большой кусок, лучше обсудить формат до реализации.
